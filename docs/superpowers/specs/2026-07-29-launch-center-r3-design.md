# Launch Center r3 — единая настройка SingBox и полный набор запусков

**Дата:** 2026-07-29  
**Статус:** дизайн утверждён владельцем

## Цель

Исправить дефекты prerelease `workplace-pilot-v0.3.0-r2`, подтверждённые на
рабочем ПК:

- Launch Center не позволяет ввести, сохранить и проверить реквизиты proxy;
- Codex Desktop с SingBox завершается `PROCESS_PROXY_NOT_SUPPORTED`;
- OpenCode с SingBox может завершиться непрозрачным `RUNTIME_NOT_VERIFIED`;
- Employee Launch Center показывает только Codex Desktop и OpenCode CLI,
  хотя установочный каталог уже содержит Codex CLI и OpenCode Desktop;
- отсутствует отдельный запуск VS Code с официальным расширением Codex.

## Границы

- Исправляются обе редакции Launch Center: Employee и Owner.
- Installer и Launch Center используют один контракт профиля соединения и
  одинаковые русские подписи полей.
- Не выполняются model calls.
- Не меняются официальные источники Codex/OpenCode и их проверки целостности.
- `employee-v0.3.0` не публикуется до успешного физического clean-PC pilot.
- Результат публикуется только как новый immutable prerelease после
  protected-main CI; существующий `workplace-pilot-v0.3.0-r2` не изменяется.

## Подтверждённые причины

1. `InstallerView.Create` связывает `ConnectionUi` только с ролью Installer.
   Для роли LaunchCenter вызывается только `LaunchCenterActions.Bind`.
2. `LaunchCenterEmployeeView.xaml` и `LaunchCenterOwnerView.xaml` содержат
   маршруты, но не содержат `ProxySettings`, полей и кнопок проверки.
3. Launch Center отображает жёстко заданные `ListBoxItem`, не полный результат
   `LaunchTargetCatalog.ForEdition`.
4. `ClientLauncher` запрещает SingBox для `launch_mode == "appx"`, потому что
   Store-приложение нельзя запустить с индивидуальными proxy-переменными.
5. `SingBoxSession.Start` заменяет конкретную ошибку `RuntimeBootstrap` общим
   `RUNTIME_NOT_VERIFIED`, поэтому пользователь не видит, отсутствует ли архив,
   повреждён ли runtime или не прошла его проверка.
6. Тесты r2 проверяли ProxySettings в Installer Employee/Owner, но не в двух
   Launch Center, поэтому частичный ремонт прошёл регрессионный набор.

## Интерфейс Launch Center

### Выбор клиента

Employee Launch Center показывает пять отдельных режимов:

1. `Codex Desktop`;
2. `Codex CLI`;
3. `VS Code — Codex`;
4. `OpenCode Desktop`;
5. `OpenCode CLI`.

Owner сохраняет свои owner-only клиенты и также получает все доступные режимы
Codex/OpenCode. Карточки строятся из единого каталога или проверяются на полное
соответствие ему, чтобы XAML больше не мог молча потерять поддерживаемую цель.

`VS Code — Codex` означает запуск уже установленного VS Code через выбранный
маршрут. Launch Center проверяет наличие официального расширения
`OpenAI.chatgpt`; при его отсутствии показывает понятное действие для перехода
к официальной странице установки. Автоматическая установка расширения без
подтверждения пользователя не выполняется.

### Настройка SingBox

При выборе `SingBox HTTP` или `SingBox HTTPS` сразу видны:

- «Сервер»;
- «Порт»;
- «Логин»;
- «Пароль»;
- кнопка «Сохранить»;
- кнопка «Сохранить и проверить».

Под полями постоянно видна последовательность:

1. заполнить реквизиты;
2. нажать «Сохранить и проверить»;
3. после успешной проверки запустить выбранный клиент.

Текст явно сообщает: Launch Center сам запускает и останавливает sing-box;
отдельный PowerShell-скрипт пользователю не нужен.

Direct и VPN скрывают блок proxy. Возврат к SingBox раскрывает его с ранее
сохранёнными непарольными значениями. Пароль сохраняется только через
существующее DPAPI-хранилище и не попадает в статусы, логи или evidence.

## Проверка и подготовка runtime

«Сохранить и проверить» выполняет единую последовательность:

1. валидирует поля;
2. сохраняет профиль;
3. проверяет upstream proxy;
4. разворачивает или проверяет локальный sing-box;
5. сообщает отдельный русский результат каждого шага.

Launch Center не заменяет конкретные причины общим `RUNTIME_NOT_VERIFIED`.
Минимально различаются:

- архив runtime отсутствует рядом с комплектом;
- SHA-256 архива не совпал;
- распаковка или запись не удалась;
- `sing-box check` отклонил конфигурацию;
- локальный proxy не начал принимать соединения.

Комплект prerelease остаётся одним ZIP. Пользовательская инструкция требует
сначала распаковать весь ZIP; Launch Center при отсутствии соседнего runtime
показывает это действие прямо в интерфейсе.

## Запуск через маршруты

### CLI, OpenCode Desktop и VS Code

Launch Center запускает точный проверенный executable с локальными
`HTTP_PROXY`, `HTTPS_PROXY` и `NO_PROXY`. После завершения клиента он
останавливает только созданный им экземпляр sing-box и удаляет временный
секретный конфиг.

Если VS Code уже открыт, Launch Center не закрывает его принудительно:
пользователь получает просьбу сохранить работу, закрыть все окна VS Code и
повторить запуск. Это необходимо, чтобы новый процесс получил выбранный
маршрут.

### Codex Desktop из Microsoft Store

Для AppX невозможно передать proxy только дочернему процессу. Поэтому на время
сессии Codex Desktop Launch Center:

1. сохраняет исходные системные proxy-настройки текущего пользователя;
2. запускает sing-box и включает системный proxy на его локальный порт;
3. активирует точный проверенный Store application identity;
4. после завершения Codex восстанавливает исходные значения;
5. при следующем запуске сначала восстанавливает оставшееся owned-состояние
   после аварийного завершения.

Интерфейс предупреждает, что в этом режиме системный proxy временно влияет на
другие приложения текущего пользователя. Никакие чужие процессы и настройки,
не зафиксированные owned-state, не останавливаются и не перезаписываются.

## Архитектура

- Общий адаптер соединения связывает один `ConnectionUi` с именами контролов
  Installer и Launch Center.
- Launch Center получает режимы из `LaunchTargetCatalog`; для VS Code вводится
  локальная integration-target, которая не подменяет официальный клиент Codex.
- `RuntimeBootstrapResult.reason` проходит до UI без потери конкретной причины.
- Для AppX добавляется отдельная owned-сессия системного proxy с атомарным
  снимком, проверкой владельца и восстановлением.
- Существующий process-only путь остаётся основным для CLI, OpenCode и VS Code.

## TDD и acceptance

RED-регрессии до production-кода покрывают:

1. ProxySettings и рабочие Save/Test существуют в Employee и Owner Launch
   Center, а не только в Installer.
2. Employee каталог и интерфейс дают все пять режимов.
3. OpenCode Desktop и Codex CLI разрешаются существующим resolver.
4. VS Code находится в поддерживаемых путях, требует официальное расширение и
   не закрывает уже открытый Code.exe.
5. Missing runtime возвращает точную причину, а не
   `RUNTIME_NOT_VERIFIED`.
6. Сохранить-и-проверить готовит runtime перед разрешением запуска.
7. AppX SingBox создаёт и восстанавливает owned system-proxy state; аварийное
   восстановление не трогает чужие значения.
8. Process-only клиенты не изменяют системный proxy.

После focused RED/GREEN обязательны:

- полный pytest;
- acceptance с `model_requests = 0`;
- сборка Employee и Owner;
- PNG-preview обоих Launch Center;
- визуальная проверка подписей, полей, кнопок, пяти карточек и отсутствия
  секретов;
- независимое code review и проверка релизного артефакта;
- PR, оба required Windows CI, merge в защищённый main;
- новый immutable prerelease r3 и повторная проверка на рабочем ПК.

## Критерий готовности

Пользователь распаковывает один Employee ZIP, открывает Launch Center, выбирает
любой из пяти режимов и SingBox, вводит реквизиты, сохраняет и проверяет их,
после чего выбранный клиент действительно запускается через маршрут. Все
временные процессы и системные настройки восстанавливаются автоматически, а
ошибки сообщают конкретное исправимое действие на русском языке.
