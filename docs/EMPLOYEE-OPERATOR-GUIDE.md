# LLM Foundation Installer — руководство оператора

## Что это за программа

Установщик разворачивает три независимые нативные базы: Codex, Claude Code и
OpenCode. Он не устанавливает сами LLM-клиенты и не выбирает модель за
пользователя. Клиент должен быть установлен заранее в принятой версии.

Внутри EXE находятся Foundation engine и только те target-пакеты, которые
прошли release acceptance. Установщик не загружает исполняемый код во время
install и не требует прав администратора.

## Что увидит сотрудник

На главном экране показаны:

- Codex, Claude Code и OpenCode с отдельными состояниями пакета и клиента;
- режим соединения;
- этапы `Проверка → План → Установка → Готово`;
- предупреждение о сохраняемых данных и автоматическом rollback;
- кнопки проверки среды и соединения.

Target можно выбрать только при двух одновременных условиях:

1. его принятый пакет встроен в EXE;
2. обнаружена точно поддерживаемая версия клиента.

Состояние `present_unbound` означает, что клиент найден, но в этом EXE нет
принятого пакета для него. `unsupported` означает несовпадение версии.

## Режимы соединения

### Direct

Используется прямой доступ. Установщик очищает у дочернего процесса переменные
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` и задаёт `NO_PROXY=*`.

### VPN

VPN считается самостоятельным транспортом. Прокси не нужен, его отсутствие не
является ошибкой или блокером. Как и в Direct, устаревшие proxy-переменные не
передаются дочернему процессу.

### Proxy

Поддерживаются:

- HTTP;
- HTTPS;
- SOCKS5 с удалённым DNS (`socks5h`);
- без авторизации;
- username/password.

Профиль без секрета хранится в
`%USERPROFILE%\.llm-foundation\connection.json`. Пароль хранится отдельно,
зашифрован Windows DPAPI для текущего пользователя. Пароль не отображается в
командной строке, отчётах и логах. Не используйте verbose-режим `curl` с
реальными учётными данными.

Кнопка проверки выполняет только явный пользовательский запрос к разрешённой
точке GitHub. Неуспешная проверка сети не запрещает offline-install из уже
проверенного EXE.

## Что происходит при установке

1. EXE проверяет встроенный Foundation engine и target-пакеты по размеру и
   SHA-256.
2. Foundation повторно проверяет package manifest, managed surface,
   preserved paths и exact client contract.
3. Команда `plan` не меняет домашнюю папку и показывает количество действий.
4. После подтверждения создаётся полный snapshot управляемой поверхности.
5. Изменения применяются атомарно под exclusive lock.
6. `doctor` сверяет установленное состояние с manifest.
7. При ошибке `doctor` автоматически запускается rollback.
8. При успехе создаётся локальный JSON-отчёт. Ошибка записи отчёта показывается
   как предупреждение и не превращает подтверждённую установку в ложный FAIL.

## Что сохраняется

Foundation изменяет только объявленную target-пакетом поверхность. В частности,
не трогаются:

- авторизация и API-ключи клиентов;
- сессии, история и архивы;
- память и состояние/SQLite;
- проекты и рабочие папки;
- browser/computer-use state;
- внешние imports;
- пользовательские плагины и темы, если target пометил их preserved.

Неизвестные старые agents/skills сначала попадают в backup и выводятся из
активного discovery. Rollback возвращает предыдущую управляемую поверхность.

## Обновление после первой установки

Поток строго односторонний:

```text
hub release → проверка immutable/attestation/SHA → plan → install → doctor
```

Сотрудник запускает `$sync-base` явно. `/sync-base` остаётся распознаваемым
алиасом там, где клиент поддерживает команду. Consumer не отправляет на hub
feedback, session-report, телеметрию, документы, локальные изменения или
учётные данные.

Проверка наличия обновления выполняется не чаще одного раза в сутки и молчит,
если новой стабильной версии нет.

## Диагностика и откат

Foundation поддерживает:

```text
plan
install
doctor
inventory
rollback
```

Установленный target хранит pinned Foundation engine внутри своей директории
`base/foundation/<version>/`. Точный путь и версия входят в manifest пакета.
Для диагностики сначала используйте `$sync-base`/`doctor`; при повреждении
состояния — `inventory`, затем `rollback`.

Локальные отчёты находятся в:

```text
%USERPROFILE%\.llm-foundation\reports\
```

## Когда EXE можно раздавать сотрудникам

Разрешён только build, у которого в `bundle-manifest.json` одновременно:

```json
{
  "signature": "valid-authenticode",
  "employee_release": true,
  "employee_distribution_allowed": true
}
```

Для этого нужны принятые stable-пакеты Codex, Claude и OpenCode, immutable
release/asset attestation, canary каждого клиента и валидная timestamped
Authenticode-подпись. Неподписанный preview раздавать сотрудникам нельзя.

## Текущий честный статус

- Foundation synthetic acceptance выполнена на fake-home в PowerShell 7 и
  Windows PowerShell 5.1.
- Нативные структуры Codex, Claude и OpenCode реализованы.
- Статический startup-context сокращён более чем на 80% для каждого target.
- Matched A/B реального provider billing ещё не запускался.
- На текущем hub обнаружен Codex; Claude Code и OpenCode отсутствуют, поэтому
  их live-canary невозможен.
- Authenticode code-signing certificate на текущем ПК отсутствует.
- Stable immutable releases и employee EXE ещё не опубликованы.

Следовательно, текущий preview предназначен для разработки и проверки, а не
для массовой установки сотрудникам.
